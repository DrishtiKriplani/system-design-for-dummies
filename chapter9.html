The Coupling Problem

When every service depends on every other service, one failure brings down the entire chain.

You place an order on Uber Eats. Behind the scenes, this happens:

Synchronous Order Flow
1
Payment Service — charges the card
↓
2
Restaurant Service — notifies the restaurant
↓
3
Driver Service — assigns a delivery partner
↓
4
Notification Service — sends push notification
↓
5
Analytics Service — records the event
↓
6
Loyalty Service — adds reward points

If this is synchronous — each service calls the next in a chain:

💥

What Goes Wrong

  • Payment is slow? Everything waits.
  • Notification service is down? Order fails.
  • Analytics has a bug? The entire chain breaks.
  • Want to add loyalty points? Touch every service in the chain.
VS
🚀

What Events Fix

  • Payment publishes an event. Done. It doesn't know who's listening.
  • Notification is down? It catches up later. Nobody else notices.
  • Analytics has a bug? Only analytics is affected.
  • Add loyalty points? Subscribe to the event. Zero code changes elsewhere.
📣

What is Event-Driven Architecture?

Services don't call each other. They emit events. Interested services react.
Emit. Don't Call.

Instead of Service A calling Service B directly, Service A publishes an event. Any service that cares about that event subscribes to it.

Key: The Payment Service has no idea these consumers exist. It just emits order.paid and moves on.

Three core components:

📣

Producers

Services that emit events when something happens. "Order was paid." "User signed up." "Item shipped." They don't know or care who's listening.

📥

Consumers

Services that subscribe to events and react. Each consumer processes the event independently at its own pace.

📩

Event Broker

The middleman that routes events from producers to consumers. Kafka, RabbitMQ, AWS EventBridge, Google Pub/Sub. The broker stores and delivers.

📄

Events

Immutable records of something that happened. Not commands ("do this") but facts ("this happened"). order.paid, not process.order.

Analogy: Think of a newspaper. The journalist writes an article (producer). The newspaper publishes it (broker). Thousands of readers consume it (consumers). The journalist has no idea who reads the article. A new reader subscribing tomorrow doesn't require the journalist to change anything.
🔬

Messaging Patterns

Not all event-driven systems work the same way. Two fundamental patterns.
📣

Pub/Sub (Publish-Subscribe)

One event, many consumers. Every subscriber gets a copy. Adding a new subscriber doesn't affect existing ones.

  • Use when: Multiple services need to react to the same event
  • Example: order.paid → restaurant, driver, notifications all get it
  • Tools: Kafka topics, SNS, Google Pub/Sub
VS
📥

Point-to-Point (Queue)

One event, one consumer. The message is delivered to exactly one worker. Used for task distribution.

  • Use when: Work needs to be processed exactly once by one worker
  • Example: Email jobs → one worker picks up each job
  • Tools: SQS, RabbitMQ queues, Kafka consumer groups
PatternConsumersDeliveryUse Case
Pub/SubManyAll subscribers get itFan-out, notifications, cross-service reactions
Point-to-PointOneExactly one consumerTask queues, job processing, work distribution

Real-world systems use both. Uber publishes ride.completed via pub/sub (billing, analytics, driver rating all subscribe). But the actual payment processing job goes into a point-to-point queue so only one worker processes it.

📚

Event Sourcing

Don't store the current state. Store every event that led to it.

In a traditional system, you store the current state: "Alice's balance is $500." When she buys something, you update the row to $450.

With event sourcing, you store every event:

Event Log for Alice's Account
1
AccountCreated — balance: $0
2
MoneyDeposited — amount: $1000
3
ItemPurchased — amount: $200, item: "headphones"
4
MoneyDeposited — amount: $500
5
ItemPurchased — amount: $800, item: "monitor"
Current balance: $0 + $1000 - $200 + $500 - $800 = $500. Replay the events to compute any state at any point in time.

Why would you do this?

🔍

Complete Audit Trail

Every change is recorded. You can answer "what happened and when" for any entity. Critical for finance, healthcare, compliance.

⏰

Time Travel

Replay events up to any timestamp. "What was Alice's balance last Tuesday at 3 PM?" Just replay events up to that point.

🔄

Replay & Rebuild

Bug in your projection logic? Fix it and replay all events. Your read model is rebuilt correctly. No data migration needed.

📈

Derived Views

Multiple read models from the same event stream. One for the dashboard, one for analytics, one for search. All derived from the same events.

Who uses this? Banks (every transaction is an event). Git (every commit is an event — the repo state is derived by replaying them). Stripe (event log for every payment state change). Event sourcing is not new — double-entry bookkeeping is event sourcing from the 15th century.

The tradeoff: Event sourcing adds complexity. Your event store grows forever. Replaying millions of events to compute current state is slow — so you need snapshots (periodic checkpoints of computed state). And event schema evolution is hard: what happens when you rename a field in an event that has 2 years of history?
🔀

CQRS — Command Query Responsibility Segregation

Separate the write path from the read path. Optimize each independently.

Most applications use the same database model for reading and writing. This works fine until reads and writes have very different requirements.

📄

Traditional (Same Model)

  • Write: INSERT order with all fields
  • Read: Complex JOIN across 5 tables to show order details with restaurant name, driver info, payment status
  • Problem: The write schema doesn't match what reads need. You either compromise writes or reads.
VS
🔀

CQRS (Separate Models)

  • Write side: Normalized, optimized for consistency. Postgres.
  • Read side: Denormalized, optimized for queries. Elasticsearch or Redis.
  • Sync: Events flow from write side to read side. Eventually consistent.

CQRS + Event Sourcing is a powerful combo:

Writes append events to the event store. Events flow to consumers that build optimized read models. The read side can be rebuilt from scratch by replaying events. Each read model is tailored to its use case — the dashboard query, the search index, the analytics view.

AspectWithout CQRSWith CQRS
Read PerformanceCompromised by write schemaOptimized read models
Write PerformanceCompromised by read indexesLean write path
ScalabilityScale reads and writes togetherScale independently
ConsistencyStrong (same DB)Eventually consistent
ComplexitySimpleMore moving parts
When to use CQRS: When your read patterns are drastically different from your write patterns. When you need to scale reads and writes independently. When you already have event sourcing. When NOT to use: Simple CRUD apps. When strong consistency is non-negotiable. When your team doesn't have experience with eventual consistency.
⚖

The Tradeoffs Nobody Tells You

Event-driven architecture trades simplicity for resilience. Know what you're signing up for.
🔍

Harder Debugging

No single request to trace. A user action might trigger 8 events across 12 services. You need distributed tracing (Jaeger, OpenTelemetry) and correlation IDs on every event.

🔄

Ordering is Tricky

Events can arrive out of sequence. order.shipped might arrive before order.paid. Your consumers must handle this gracefully.

⏰

Eventual Consistency

The read model lags behind the write. A user places an order and immediately checks their order history — it might not be there yet. Design your UX for this.

💥

Failed Events

What happens when a consumer fails to process an event? You need retry logic, Dead Letter Queues (DLQs), and idempotent consumers (processing the same event twice produces the same result).

The rule of thumb:

ScenarioBest ApproachWhy
Few services, simple flowsHTTP / RESTSimpler. Easier to debug. Strong consistency.
High fan-out, independent side effectsEventsDecoupled. Resilient. Easy to extend.
Need audit trail + time travelEvent SourcingComplete history. Replay. Rebuild.
Reads ≠ Writes at scaleCQRSOptimize each path independently.
Simple CRUD, 3 servicesDon't use eventsUnnecessary complexity. HTTP is fine.

The staff-level insight: The question isn't "should we use event-driven architecture?" It's "which interactions in our system benefit from decoupling, and which need synchronous guarantees?" Most production systems use both — HTTP for request-response flows, events for fan-out and side effects.

💼

The System Design Interview

"How do you handle side effects across multiple services?"
"Design an order processing system for a food delivery app. When a user places an order, the restaurant must be notified, a driver assigned, and the user gets a confirmation."
✘ THE REJECTED ANSWER
"The order service calls the restaurant service, then the driver service, then the notification service synchronously in sequence."
Interviewer thinking: "If any of those services is slow or down, the user's order fails. This doesn't scale."
Same question. Better answer.
✔ THE STAFF-LEVEL ANSWER
"The order service validates the order and processes payment synchronously — that needs strong consistency. Once payment succeeds, it publishes an order.paid event to Kafka. The restaurant service, driver service, and notification service each subscribe independently. Each consumer is idempotent — processing the same event twice produces the same result. Failed events go to a Dead Letter Queue for investigation. I'd add correlation IDs for distributed tracing across all consumers. The read model for the user's order history is eventually consistent — the UI shows a 'processing' state until all downstream services confirm."

What interviewers look for:

🔀

Sync vs Async Reasoning

Know which parts need synchronous guarantees (payment) and which can be async (notifications, analytics).

💥

Failure Handling

Mention idempotency, retries, DLQs. "What happens when a consumer fails?" separates good from great.

🔍

Observability

Correlation IDs, distributed tracing. Show you've thought about debugging in a decoupled system.

⚖

Consistency Tradeoffs

Acknowledge eventual consistency. Explain how the UX handles the lag (optimistic UI, processing states).

🎯

Key Takeaways

What to remember about Event-Driven Architecture
📣

Emit, Don't Call

Services publish events instead of calling each other. This decouples them — add new consumers without changing producers.

📚

Events Are Facts

Events record what happened, not what should happen. They're immutable. Event sourcing stores every fact. The current state is derived.

🔀

CQRS Splits Read/Write

When reads and writes have different needs, optimize them separately. Powerful with event sourcing. Overkill for simple CRUD.

⚖

Know the Tradeoffs

Eventual consistency, harder debugging, ordering challenges. Use events for fan-out. Use HTTP for request-response. Most systems need both.
