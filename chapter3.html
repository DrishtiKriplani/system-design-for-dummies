SQL vs NoSQL

A spreadsheet with rules vs a filing cabinet with freedom
🗃

SQL (Relational)

  • Schema: Fixed, predefined tables
  • Guarantees: ACID transactions
  • Relationships: Joins & foreign keys
  • Scaling: Vertical (scale up)
Used by: Notion · Stripe · Instagram · GitHub
VS
📃

NoSQL (Non-Relational)

  • Schema: Flexible, dynamic
  • Guarantees: BASE (eventual consistency)
  • Relationships: Embedded, denormalized
  • Scaling: Horizontal (scale out)
Used by: Netflix · Discord · Uber · Coinbase
Analogy: SQL is Excel with strict columns — every row follows the same structure. NoSQL is a folder of JSON files — each document can look different.
📄

Document Store

MongoDB, CouchDB. JSON-like docs. Flexible schema. Best for: content, catalogs.

🔑

Key-Value Store

Redis, DynamoDB. O(1) lookups. Best for: caching, sessions, leaderboards.

📊

Wide-Column

Cassandra, HBase. Column families. Best for: time-series, write-heavy workloads.

🔗

Graph Database

Neo4j, Neptune. Nodes & edges. Best for: social networks, recommendations.

Plot twist: most companies use both. Stripe runs PostgreSQL for payments + Redis for caching. Uber uses MySQL for trips + Cassandra for driver locations. This is called polyglot persistence.

🔍

Indexing

The difference between 2ms and 20 seconds is one line of SQL

An index is a lookup structure that lets the database find rows without scanning every record. Think of it as a book's table of contents — without it, you'd read every page to find what you need.

SELECT * FROM users WHERE email = 'alice@example.com' — 50M rows
No Index
50,000,000 rows scanned — 23.4s
B-tree Index
26 lookups — 0.002s
Same query. Same data. 11,700x faster with one index.
Analogy: Finding a name in a phonebook by reading every entry (full scan) vs using the alphabetical tabs (index). The data is the same — the access pattern changes everything.
🌳

B-tree

Default for most databases. Equality + range queries. O(log n). Handles 90% of use cases.

#

Hash Index

O(1) exact match only. No range support. Fast for lookups like session tokens.

📚

Composite

Multi-column. (country, city) helps queries filtering by country or both — but NOT city alone.

🔎

GIN / Full-text

Inverted index for text search, JSONB, arrays. Powers PostgreSQL full-text search.

The tradeoff: every index you add slows every write because the DB updates both the table and the index. At 10 indexes, write throughput drops to ~20% of baseline. Index what you query. Delete what you don't.

🔀

Sharding

When one database can't handle it, split into many

When vertical scaling hits a wall (biggest AWS RDS: 64 vCPU, 512GB RAM), you shard — split data across multiple independent databases. Each shard holds a subset.

Analogy: A restaurant that's too busy doesn't build a bigger kitchen — it opens more locations. Each location serves a different neighborhood.

Hash-Based

hash(key) % N. Even distribution but no range queries. Used by DynamoDB, Cassandra.

📈

Range-Based

A-M shard 1, N-Z shard 2. Range scans work but hot spots risk. Used by HBase.

🔄

Consistent Hashing

Hash ring. Adding shards moves minimal data. Used by most distributed systems.

🔑

Shard Key = Everything

Bad key (country) = US shard gets 60%. Good key (user_id) = even distribution.

Notion's approach: 480 logical shards across 96 machines, partitioned by workspace_id. Users in same workspace hit same shard. But they ran single Postgres for years first. Don't shard until you must — try replicas, caching, and better indexes first.

🔁

Replication

One copy of your data is a single point of failure

Replication keeps copies of your database on multiple servers. If one dies, another takes over. Reads get distributed for higher throughput.

Analogy: Making photocopies of an important document. If one gets destroyed, you have backups. But you need to keep all copies updated when the original changes.

Consistency Models

Not everything needs to be perfectly in sync

Consistency isn't binary. It's a spectrum — and the right level depends on the operation, not the database.

Analogy: Strong consistency is a live broadcast — everyone sees events at the same time. Eventual consistency is a newspaper — everyone gets the news, just not all at once.

The golden rule: use the weakest consistency your operation can tolerate. Every step stronger = more latency and less throughput. Consistency is not a database choice — it's a per-operation choice.

Key Takeaways

Design decisions that outlive your sprint
🔍

Access Patterns First

SQL vs NoSQL is the wrong question. Start with how your app reads and writes data.

📈

Index Strategically

A missing index is a time bomb. Too many indexes slow every write. Use EXPLAIN ANALYZE.

🔀

Shard When You Must

Notion ran one Postgres for years. Don't shard prematurely — but plan your shard key early.

⚖

Consistency Per Operation

Bank balance = strong. Like count = eventual. Match the model to the operation.
