The Bouncer Your API Needs

The Cloudflare Incident

When the company that sells rate limiting forgot to rate limit itself.
☁
Cloudflare Dashboard Outage
September 12, 2025 — ~2 hours of downtime

Cloudflare's dashboard went down for approximately 2 hours. Not from a DDoS attack. Not from a hacker. From their own frontend code.

A developer added an object to a React useEffect dependency array. React saw a "new" object on every render (because objects are compared by reference, not value). The effect re-ran. Each run called the Tenant Service API. Each response triggered a re-render. Each re-render triggered another call.

One dashboard tab = hundreds of API calls per second.

Rate Limit Added

Thousands of engineers had the dashboard open. Millions of requests hit one internal API. It buckled. The dashboard became inaccessible.

The fix? Add a global rate limit on the Tenant Service API.

The lesson: Rate limiting isn't just for external users. Your own code can be your worst attacker. If you don't rate limit internally, your system will eventually rate limit itself — by failing.

🛡

Why Rate Limiting Matters

It's not just about blocking bad actors. It's about protecting the entire system.
💥

Prevent Resource Exhaustion

One user sending 10,000 requests/second can exhaust database connections, CPU, and memory — affecting every other user on the platform.

💰

Control Costs

Every API call costs compute. Uncontrolled usage = unpredictable cloud bills. Rate limiting puts a ceiling on cost per user.

🔒

Mitigate Abuse

Brute-force login attempts, credential stuffing, scraping — all rely on high request volume. Rate limiting makes these attacks impractical.

⚖

Fair Usage

Without limits, one power user can monopolize shared resources. Rate limiting ensures equitable access across all users.

The bouncer analogy: A rate limiter is the bouncer at the door of a nightclub. It doesn't check if you belong. It checks if you're coming in too fast. One person entering every few seconds? Fine. 50 people rushing the door at once? Line up or go home.

What the user sees: HTTP status 429 Too Many Requests. Usually accompanied by a Retry-After header telling the client when to try again.

The Four Algorithms

Each one answers the same question differently: "How do we say no — without saying no too late?"
🏊
Token Bucket
Used by AWS API Gateway, Stripe, GitHub API

Imagine a bucket that holds tokens. Tokens are added at a fixed rate (e.g., 10 tokens per second). Each request costs one token. If the bucket has tokens, the request goes through and a token is removed. If the bucket is empty, the request is rejected.

The bucket has a maximum capacity. Tokens accumulate when traffic is low, up to the bucket size. This allows controlled bursts — a user who was idle for a while can send a burst of requests up to the bucket capacity, then must slow down to the refill rate.

Strengths

Allows controlled bursts. Memory efficient (just two numbers: tokens + timestamp). Simple to implement. Most popular algorithm in production.

Tradeoffs

Two parameters to tune (bucket size + refill rate). Getting the burst size right requires understanding your traffic patterns.

💧
Leaky Bucket
Used by Shopify, NGINX

Imagine a bucket with a hole at the bottom. Requests pour in from the top. They drain out (get processed) at a constant rate through the hole. If the bucket overflows (too many requests queued), new requests are dropped.

Unlike token bucket, leaky bucket doesn't allow bursts. It smooths traffic into a perfectly uniform output rate. 1000 requests arrive at once? They're processed one by one at the drain rate. The rest wait in the queue.

Strengths

Perfectly smooth output. Protects downstream systems from spikes. Great for payment processing, checkout flows.

Tradeoffs

No burst tolerance. A legitimate traffic spike is treated the same as an attack. Queued requests add latency.

🕒
Fixed Window Counter
Common in simple APIs, internal services

Divide time into fixed windows (e.g., 1-minute intervals). Each window has a counter. Every request increments the counter. When the counter hits the limit, reject until the next window starts.

The boundary problem: If the limit is 100 requests/minute, a user can send 100 requests at 11:59:59 and 100 more at 12:00:00 — that's 200 requests in 2 seconds, while technically staying within the "100 per minute" limit in each window.

Strengths

Dead simple. One counter per user per window. Minimal memory. Easy to implement with Redis INCR + EXPIRE.

Tradeoffs

Boundary burst problem lets users effectively double their limit. Not suitable when strict enforcement matters.

📈
Sliding Window
Used when precision matters

Sliding Window Log: Store the timestamp of every request. To check the limit, count all timestamps within the last window (e.g., last 60 seconds). Most accurate — but stores a timestamp per request. At high volume, that's a lot of memory.

Sliding Window Counter (optimized): Combine two fixed windows with a weighted average. If we're 30 seconds into the current minute, the effective count = (current window count) + (previous window count × 0.5). No timestamp storage needed. Good accuracy with minimal memory.

Strengths

No boundary burst problem. Accurate rate enforcement. The counter variant gives near-exact results with minimal memory.

Tradeoffs

Log variant is memory-heavy. Counter variant is approximate (but close enough for most use cases).

Rule of thumb:

Token Bucket → when you need controlled bursts (most APIs)
Leaky Bucket → when you need smooth, constant throughput (payments, checkout)
Fixed Window → when you need simplicity above all (internal tools)
Sliding Window → when you need precision (strict compliance, billing APIs)

The Distributed Problem

One algorithm on one server is easy. The real challenge: multiple servers, shared state, race conditions.

You have 5 API servers. User limit: 100 requests/minute.

500 requests get through

Each server has its own counter. Each allows 100. The user sends 100 to each server. 5 × 100 = 500.

This is the distributed rate limiting problem. Local counters don't work when requests are load-balanced across multiple servers.

Solution 1: Centralized Counter (Redis)

Every server checks and increments a shared counter in Redis before processing the request. Redis's INCR command is atomic — no race conditions. Combined with EXPIRE, you get a complete fixed-window rate limiter in two commands.

Tradeoff: Every request now requires a Redis round-trip. At high throughput, Redis becomes the bottleneck. If Redis goes down, you either fail open (allow all traffic) or fail closed (block everything). Both are risky.

Solution 2: Local + Sync

Each server maintains a local counter and periodically syncs with a central store. Faster (no per-request network call) but less accurate — you might temporarily exceed the limit between sync intervals.

Solution 3: Sticky Sessions

Route all requests from the same user to the same server (via consistent hashing on user ID). Each server only needs a local counter for its users. No shared state needed. Tradeoff: uneven load distribution and loss of counter if the server goes down.

ApproachAccuracyLatencyFailure Mode
Centralized (Redis)Exact+1 network hopRedis down = no limiting
Local + SyncApproximateNo added latencyGraceful degradation
Sticky SessionsExact (per server)No added latencyCounter lost on server failure

Production reality: Most systems use Redis-based rate limiting with circuit breakers. If Redis is unreachable, fail open for a short window rather than blocking all traffic. Stripe, GitHub, and Discord all use this pattern.

Where to Place Rate Limiting

The earlier you reject, the less work your system does.
Request Path
1
CDN / Edge — Cloudflare, Akamai. Block at the network edge before requests even reach your infrastructure. Cheapest place to reject.
↓
2
API Gateway — Kong, AWS API Gateway. Centralized rate limiting across all services. Most common placement.
↓
3
Load Balancer — NGINX, HAProxy. Per-IP or per-route limiting before requests hit application servers.
↓
4
Application Layer — Middleware in your service. Fine-grained, per-user, per-endpoint limits. Most flexible but most expensive (request already reached your code).
Best practice: Layer rate limiting. Coarse limits at the edge + fine-grained limits at the application layer. Defense in depth.
Think of it like airport security: You don't wait until someone is on the plane to check their ticket. You verify at the gate, then security, then boarding. Each layer catches something the previous one might miss.

The System Design Interview

"Design a rate limiter" — One of the most common system design questions.
"Design a rate limiter for an API that handles 10,000 requests per second."
✘ THE REJECTED ANSWER
"I'll count requests per user and block them when they exceed the limit. I'll use a database to store the counts."
Interviewer thinking: "A database query on every request at 10K RPS? That's creating the problem you're trying to solve."
Same question. Better answer.
✔ THE STAFF-LEVEL ANSWER
"I'd use a token bucket algorithm with Redis as the backing store. Each user gets a key in Redis with their token count and last refill timestamp. On each request, I atomically check and decrement using a Lua script to avoid race conditions. The API gateway enforces coarse per-IP limits, and the application layer enforces per-user, per-endpoint limits. If Redis goes down, I fail open with local in-memory counters as a fallback — slightly less accurate but the system stays available. I'd return 429 with Retry-After headers and include X-RateLimit-Remaining headers so clients can self-throttle."

Key things interviewers look for:

⚙

Algorithm Choice + Why

Don't just name an algorithm. Explain why token bucket fits (allows bursts, low memory) vs. alternatives.

🌐

Distributed Awareness

Multiple servers = shared state problem. Mention Redis, race conditions, atomic operations.

💥

Failure Handling

What happens when Redis goes down? Fail open or closed? This separates good from great answers.

📋

Client Experience

Return proper headers (429, Retry-After, X-RateLimit-Remaining). Good APIs help clients behave well.

Key Takeaways

What to remember about Rate Limiting
🛡

Protect Everything

Rate limit external APIs, internal services, and even your own frontend. Cloudflare's incident proves internal traffic can be just as dangerous.

⚙

Pick the Right Algorithm

Token Bucket for bursts. Leaky Bucket for smooth traffic. Fixed Window for simplicity. Sliding Window for precision. No single algorithm fits all cases.

🌐

Distributed is Hard

Local counters don't work across multiple servers. Use Redis for shared state, but plan for Redis failure with fallback strategies.

📍

Layer Your Defense

Coarse limits at the edge, fine-grained limits at the application. The earlier you reject, the less work your system does.
