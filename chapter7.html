Without any protection, that $500 vanishes. Alice is debited. Bob is never credited. The database has no memory of what it was trying to do.

This is the fundamental problem every database must solve: what happens when a write is interrupted halfway through?

The answer, used by virtually every database on earth, is three words: Write-Ahead Logging.

📝

What is Write-Ahead Logging?

One rule. Before changing any data, write what you're about to do to a log. First. Always.

WAL is a protocol, not a tool. The rule is simple:

Log before data.

The log record must hit disk before the corresponding data change is written. No exceptions.

Think of it like a pilot's checklist. Before takeoff, every action is written down. If something goes wrong mid-flight, the checklist tells you exactly what was done and what wasn't. The database's WAL is that checklist.

💥

Without WAL

  • Crash mid-write: Data file is half-updated, corrupted
  • On restart: No way to know what was in progress
  • Result: Data loss, inconsistency, manual recovery
  • Impact: Missing transactions, orphaned records
VS
📛

With WAL

  • Crash mid-write: Data file may be corrupt, but the log is intact
  • On restart: Replay the log, redo committed work, undo the rest
  • Result: Consistent state restored automatically
  • Impact: Zero data loss for committed transactions
Analogy: Imagine writing an exam in pencil directly on the answer sheet vs. first drafting answers on a rough sheet. If someone snatches the answer sheet mid-exam, your rough sheet has everything you did. You can reconstruct it. The WAL is your rough sheet.
⚙

How WAL Works: Step by Step

The lifecycle of a single database write, from query to durability.
The WAL Write Path
1
Transaction begins. User executes UPDATE accounts SET balance = balance - 500 WHERE user = 'Alice'
↓
2
Write to WAL buffer. The change is recorded as a WAL record in memory. "Debit $500 from Alice, page 42, offset 128."
↓
3
Flush WAL to disk (fsync). The WAL record is forced to permanent storage. This is the durability guarantee. Until this completes, the transaction is not committed.
↓
4
Modify data page in memory. The actual data buffer (Alice's row) is updated in RAM. This is the "dirty page." It hasn't reached disk yet.
↓
5
Transaction commits. The database acknowledges the write to the client. The data file may not be updated yet — but the WAL is on disk. That's enough.
↓
6
Checkpoint (later). Periodically, dirty pages are flushed to disk. The WAL records before this point can be recycled. This is how the WAL stays bounded in size.
Key insight: Steps 1–5 happen on every write. Step 6 happens in the background. The data file is always behind the WAL. That's by design.

Why not just write data directly to disk?

Because data files have random write patterns. Alice's row is on page 42. Bob's is on page 7891. Updating both means two random disk seeks. Slow.

The WAL is a sequential, append-only file. Every write goes to the end. Sequential writes are 10–100x faster than random writes on both SSDs and spinning disks. The WAL absorbs the write speed, and the data files catch up later.

Write PatternHDD SpeedSSD SpeedWAL Uses
Sequential (append)100–200 MB/s500–3000 MB/sYes
Random (in-place)0.5–2 MB/s50–500 MB/sNo
The staff-level detail: Postgres enables full_page_writes by default. After every checkpoint, the first modification to each data page writes the entire page to WAL, not just the change. Why? Because a crash during an OS-level page write can leave a half-written page. Storing the full page image in WAL guarantees it can be restored correctly. This is called torn page protection.
🔄

Crash Recovery: What Happens on Restart

The database starts up. It doesn't know if the last shutdown was clean. Here's the recovery protocol.
Recovery Process
1
Read checkpoint record. Find the last known consistent state. This is the starting point for recovery.
↓
2
Scan WAL forward from checkpoint. Read every WAL record from the checkpoint to the end of the log.
↓
3
REDO committed transactions. Replay all changes from committed transactions that may not have made it to data files. If the page already has the change, skip it.
↓
4
UNDO uncommitted transactions. Any transaction that started but never committed is rolled back. The partial changes are removed.
Result: Database is back to a consistent state. Committed work is preserved. Uncommitted work is discarded. Zero data loss.

Back to Alice and Bob: the database replays the WAL. It sees "debit Alice $500" was committed but "credit Bob $500" was not. It undoes the debit. Alice's balance is restored. No money is lost.

Or, if both the debit and credit were committed before the crash — it redoes both. Bob gets his money. Either way, the database is consistent.

⏰

Recovery Time

Proportional to WAL generated since last checkpoint. Frequent checkpoints = faster recovery. Tradeoff: more I/O during normal operations.

📄

Idempotent Replay

WAL replay is safe to run multiple times. Each record includes enough info (page ID, offset, LSN) to detect if it's already applied. Replaying twice produces the same result.

🔒

Write Durability

A transaction is only committed after its WAL record hits disk via fsync. Not when data is written. Not when the client is notified. When the WAL is flushed.

⚠

Disk Failure ≠ WAL Recovery

WAL protects against process/power crashes, not disk failure. For that you need replication or backups. WAL assumes the disk itself is reliable.

🚀

Beyond Crash Recovery

WAL isn't just a safety net. It's the primitive that powers replication, CDC, and time travel.

Once you have a sequential log of every change, you can do much more than recover from crashes.

🔁

Streaming Replication

Postgres streams WAL records to replicas in real time. The replica replays them, staying in sync with the primary. That's how read replicas work — they're just WAL replay machines.

📊

Change Data Capture (CDC)

Debezium reads the Postgres WAL and streams every row-level change to Kafka. No application code changes. No triggers. The WAL is the source of truth, and CDC just reads it.

⏰

Point-in-Time Recovery (PITR)

Keep a base backup + archived WAL files. Replay WAL up to any specific timestamp. "Restore the database to exactly 2:47 PM last Tuesday." That's PITR.

📋

Logical Decoding

Postgres can decode WAL into human-readable changes: "INSERT into users: id=42, name='Alice'." This powers real-time event streaming from the database without polling.

The staff-level insight: Crash recovery, replication, CDC, and PITR are not four separate systems. They are four consumers of the same WAL. One log. Four use cases. This is why WAL is the most important primitive in database architecture.

How Netflix Built a WAL for Their Entire Data Platform

Not a database WAL. A platform-wide WAL that captures, guarantees, and delivers every data change.
🎬
Netflix Tech Blog
"Building a Resilient Data Platform with Write-Ahead Log at Netflix"

Netflix published a detailed blog on how they built a generic WAL abstraction across their data platform. This isn't a database-level WAL — it's a distributed system primitive that sits between services and datastores.

The problems Netflix faced:

💥

Accidental Data Loss

Writes to databases would occasionally fail silently. Without a durable log of intent, there was no way to detect or recover missing writes.

🔄

Data Corruption

Partial writes or race conditions across services would corrupt data. No single source of truth existed to reconcile what happened.

📋

Multi-Datastore Sync

Netflix writes to Cassandra AND Elasticsearch for the same data. Keeping them in sync without a shared log was fragile and error-prone.

⏰

Delayed Processing

Many services needed "execute this later" semantics — delay queues. Building them from scratch every time was wasteful and unreliable.

Netflix's solution: a generic WAL with one API.

WriteToLog(data, options)

One endpoint. The WAL captures the data change, guarantees durability, and delivers it to downstream consumers. The underlying queue technology (Kafka, SQS, etc.) is abstracted away — swappable without code changes.

What Netflix uses their WAL for:

Use CaseHow WAL Helps
Delay QueuesOffload a request to WAL with a delay. WAL guarantees delivery after the specified time. Most common use case.
Cross-Region ReplicationWAL captures writes in one region and reliably replays them in others — even for datastores that don't natively support replication.
Secondary IndicesWhen data is written to Cassandra, WAL delivers the change to Elasticsearch to keep the search index in sync.
Multi-Partition UpdatesCoordinating writes across multiple partitions or datastores. WAL provides the durability and ordering guarantee.

The staff-level insight from Netflix's approach:

Netflix recognized that WAL is not just a database concept. It's a distributed systems primitive. Any time you need to guarantee that a data change is durable and eventually delivered — regardless of crashes, network failures, or downstream outages — you need a write-ahead log.

Their abstraction proves that the same principle Postgres uses internally for crash recovery can be lifted to the application layer to solve data durability, multi-datastore consistency, and delayed processing at platform scale.

Key insight: Database WAL protects one database from crashes. Netflix's WAL protects an entire distributed data platform from data loss, inconsistency, and failed deliveries. Same principle. Bigger blast radius.

The System Design Interview

"How does the database guarantee durability?" — The question behind every storage design.
"You're designing a payment system. How do you ensure no transaction is lost during a crash?"
✘ THE REJECTED ANSWER
"I'll use a reliable database like Postgres. It handles durability automatically."
Interviewer thinking: "They don't understand how durability actually works."
Same question. Better answer.
✔ THE STAFF-LEVEL ANSWER
"The database uses write-ahead logging. Before any data change hits the data file, the intent is written to a sequential, append-only log and fsynced to disk. If the server crashes, on restart it replays the WAL — redoing committed transactions and undoing incomplete ones. This is how Postgres, MySQL, and every serious database guarantees ACID durability. For our payment system, I'd also ensure WAL archiving is enabled for point-in-time recovery, and stream the WAL to a standby replica for high availability."

When to bring up WAL in interviews:

💰

"Design a payment system"

Durability is non-negotiable. WAL + fsync + replication is the standard answer for "how do you not lose money."

📃

"Design a database"

WAL is the foundation. Write path, recovery, replication — all built on the same log. Show you understand the internals.

📊

"How do you keep two datastores in sync?"

CDC via WAL. Debezium reads the WAL and streams changes to Kafka. No dual-write bugs. The WAL is the single source of truth.

🔄

"How does replication work?"

Streaming replication = shipping WAL records to replicas. The replica is a WAL replay machine. Show you know it's not magic.

The golden phrase: "WAL gives us durability, replication, CDC, and point-in-time recovery — all from the same mechanism. It's one log serving four purposes."

Key Takeaways

What to remember about Write-Ahead Logging
📝

Log Before Data

The WAL record hits disk before the data change. That's the entire durability guarantee. Everything else follows from this one rule.

🔄

One Log, Many Uses

Crash recovery, replication, CDC, PITR — all consumers of the same WAL. Understanding WAL means understanding how databases actually work.

🎬

WAL Beyond Databases

Netflix built a platform-wide WAL for data durability, cross-region replication, and delay queues. The concept scales beyond a single database.

⚡

Sequential Writes Win

WAL is fast because it's append-only. Sequential writes are 10–100x faster than random. The data files catch up later via checkpoints.
