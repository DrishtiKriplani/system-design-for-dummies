Caching Strategies
The Art of Not Hitting Your Database

A database query takes 5–50ms. A cache lookup takes 0.1ms. That's a 500x difference. Multiply by millions of requests and caching is the difference between fast and broken.

Caching stores frequently accessed data closer to where it's needed. The closer to the user, the faster the response. But caching seems simple until you pick the wrong strategy — and then it silently breaks your system.

Analogy: A cache is like keeping your most-used tools on your desk instead of in the garage. You could walk to the garage every time (database), or just reach for the desk (cache). But if someone rearranges the garage and your desk still has the old tools — you're working with stale data.

The Four Caching Strategies

Same goal, different tradeoffs. Each one answers: when do you read from cache, and when do you write to it?
🔎
Cache-Aside (Lazy Loading)
Used by most web apps • Redis + Postgres

The application manages the cache directly. On read: check cache first. If it's a miss, read from DB, then write the result to cache. On write: update DB, then invalidate the cache.

App → Cache → miss → DB → result → Cache (SET)
Strengths

Only caches data that's actually requested. No wasted memory. Simple to implement. Most popular pattern.

Risks

First request is always slow (cache cold). Stale data if DB updates without cache invalidation. Cache stampede on popular key expiry.

📝
Write-Through
Used by DynamoDB DAX • Consistent reads

Every write goes to both cache and DB simultaneously. The cache is always fresh — reads never hit stale data.

App → write → Cache → sync → DB
Strengths

Cache is always consistent with DB. No stale reads. Great when read-after-write consistency matters.

Risks

Write latency doubles (two writes per operation). Cache fills with data that may never be read. Wasted memory.

💥
Write-Behind (Write-Back)
Used by CPU caches • Disk controllers

Write to cache first, return immediately. Flush to DB asynchronously later. The fastest write path — but the most dangerous.

App → write → Cache → ACK  ...async... → DB
Strengths

Fastest writes. App gets instant ACK. Can batch DB writes for efficiency. Absorbs write spikes.

Risks

Data loss if cache crashes before flush. Complexity of async flush logic. Rarely used at application layer — common in hardware (CPU, SSD).

📚
Read-Through
Used by CDNs • Hibernate L2 Cache

The cache sits between the app and DB transparently. App only talks to cache. On a miss, the cache itself reads from DB and stores the result.

App → Cache → miss → DB → cache fills itself → App
Strengths

App code is simple — just reads from cache. Cache handles all DB interaction. Clean separation of concerns.

Risks

First read is slow. Cache layer becomes a single point of failure. Less control over what gets cached.

The difference between Cache-Aside and Read-Through is subtle but important: in Cache-Aside, the app manages cache misses. In Read-Through, the cache layer handles misses transparently. Same result, different responsibility.

Cache Stampede (Thundering Herd)

When a popular cache key expires and thousands of requests simultaneously try to rebuild it.

A popular key expires. 10,000 requests arrive in the next second. All see a cache miss. All query the database. All try to write the result back to cache. The database gets 10,000 identical queries instead of 1.

Three solutions:

🎲

TTL Jitter

Randomize expiry times. Instead of all keys expiring at exactly 60s, expire between 55–65s. Keys don't all go cold at once. Simple. Effective. First line of defense.

🔒

Locking (Mutex)

On cache miss, acquire a lock (Redis SETNX). Only one request rebuilds the cache. Others wait or serve stale data. Prevents duplicate DB queries.

⏰

Early Recompute

Probabilistically refresh the cache before it expires. If TTL is 60s, start refreshing at 50s with increasing probability. Cache never actually goes cold.

📄

Stale-While-Revalidate

Serve stale data immediately while refreshing in the background. User gets a fast response. Cache gets updated. HTTP uses this exact header.

The Shopify fix: TTL jitter + mutex locking. Randomize expiry so keys don't all die at once. If they do, only one request rebuilds while others serve stale data. Two lines of defense.
🌐

Distributed Caching

When one Redis instance isn't enough.

A single Redis instance handles 100K+ ops/sec. But at scale, you need multiple cache nodes. This brings familiar challenges — which node holds which key?

Consistent hashing (Chapter 6) is the answer. Keys and nodes sit on a ring. Add a node → only 1/N keys move. The cache stays warm through scaling events.

ApproachHow It WorksTradeoff
Redis Cluster16,384 hash slots distributed across nodes. Automatic resharding.Built-in, production-ready
Client-Side ShardingApp decides which node via consistent hashing.Simple but no auto-failover
Redis SentinelPrimary-replica with automatic failover.High availability, not horizontal scale
MemcachedMulti-threaded, client-side distribution. No replication.Fast but no persistence
Netflix's EVCache: Distributed caching layer built on Memcached. 2 trillion requests per day across tens of thousands of nodes. Uses consistent hashing for routing. Handles 30 million ops/sec at peak.

The System Design Interview

"How would you add caching to this system?"
"Your API is slow. P99 latency is 800ms. Most of the time is spent in database queries. How do you fix it?"
✘ THE REJECTED ANSWER
"I'll add Redis in front of the database. Cache everything."
Interviewer thinking: "Cache everything? What about invalidation? Stale data? Memory limits? This is a red flag."
Same question. Better answer.
✔ THE STAFF-LEVEL ANSWER
"First, I'd profile to find the hot queries — 20% of queries usually drive 80% of load. I'd use cache-aside with Redis for those specific queries. TTL of 5 minutes with jitter to prevent stampedes. For cache invalidation, I'd invalidate on write to the same entity. For popular keys, I'd add mutex locking so only one request rebuilds on expiry. I'd monitor cache hit rate — below 90% means the TTL is too short or we're caching the wrong things. For the distributed layer, Redis Cluster with consistent hashing. And I'd design the system to degrade gracefully — if Redis goes down, requests fall through to the database. Slower, but not broken."

What interviewers look for:

🔎

Strategy Choice + Why

Name the strategy. Explain why cache-aside fits. Mention the tradeoff with stale data.

💥

Invalidation Strategy

"How do you keep cache and DB in sync?" TTL, write-through invalidation, event-driven invalidation.

🚨

Stampede Awareness

Mention TTL jitter, mutex locking. This separates someone who's read about caching from someone who's operated it.

📈

Metrics

Cache hit rate, eviction rate, memory usage. If you can't measure it, you can't optimize it.

🎯

Key Takeaways

What to remember about Caching Strategies
🔎

Cache-Aside Is Default

Most apps start here. Check cache, miss goes to DB, write result back. Simple, effective, battle-tested.

📝

Know All Four

Cache-Aside, Write-Through, Write-Behind, Read-Through. Each has a use case. Picking wrong is worse than not caching.

🚨

Stampede Prevention

TTL jitter + mutex locking. Two lines of defense against the most common cache failure mode.

📋

Invalidation Is Hard

"There are only two hard things: cache invalidation and naming things." Design your invalidation strategy before you cache.
