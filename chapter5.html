The Kafka Dilemma

Why every candidate puts Kafka in their system diagram — and why interviewers cringe.

"I'd put Kafka here… and here… and maybe here…"

Kafka Is Not a Hammer

Kafka is powerful. But slapping it between every service in your diagram doesn't make you a staff engineer — it makes you someone who learned one tool.

Here's the truth that separates mid-level from staff-level answers: the tool choice matters less than the justification. Interviewers don't want to hear "I'd use Kafka." They want to hear why Kafka over SQS, RabbitMQ, or even a simple database polling mechanism.

This chapter covers every Kafka concept you need — from brokers to exactly-once semantics — and, more importantly, teaches you when to use it and when to walk away.

The restaurant analogy: A message queue is like a kitchen order counter. The waiter (producer) places an order slip, then immediately goes back to serving tables. The chef (consumer) picks up orders at their own pace. The counter (queue) absorbs the rush. Nobody waits. Nobody crashes.
📜

What is Apache Kafka?

A distributed event streaming platform, originally built at LinkedIn.

Kafka is a distributed, append-only commit log that lets services publish and subscribe to streams of events. Unlike traditional message queues (RabbitMQ, SQS), Kafka retains messages after consumption — making replay, auditing, and reprocessing possible.

Think of Kafka as a distributed, fault-tolerant, horizontally scalable append-only log. Producers write events to the end of the log. Consumers read from any position. The log is split into partitions spread across brokers. That's the entire mental model.

📝

Append-Only Log

Messages are immutable. Once written, they can't be modified or deleted (until retention expires). This is what enables replay.

🔄

Pull-Based Consumers

Unlike RabbitMQ (push), Kafka consumers pull at their own pace. Slow consumers don't crash — they just fall behind.

💾

Persistent Storage

Messages are written to disk, replicated across brokers. Surviving broker failures is built into the DNA.

✍

Zero-Copy Transfer

Kafka sends data from disk to network socket without copying to userspace — the secret behind its insane throughput.

📚

Core Concepts: The Full Picture

Every Kafka term you'll encounter in interviews, explained with real examples.
📦

Broker

A single Kafka server. It receives messages from producers, stores them on disk, and serves them to consumers. A Kafka cluster is just multiple brokers working together.

Real world: LinkedIn runs 100+ brokers per cluster. Each broker handles thousands of partitions and terabytes of data.
📃

Topic

A named stream of events. Think of it as a category or feed name. Producers write to a topic. Consumers read from a topic. Topics are split into partitions.

Real world: order-events, user-signups, payment-completed, page-views
▮▮▮

Partition

A topic is split into partitions — ordered, immutable sequences of messages. Partitions are distributed across brokers for parallelism. Messages within a partition are strictly ordered. Across partitions, there's no ordering guarantee.

Real world: A topic with 12 partitions can have 12 consumers reading in parallel. Uber uses partition keys (user_id) to ensure all events for the same rider hit the same partition — preserving order.
🔑

Partition Key

Determines which partition a message goes to. Messages with the same key always land in the same partition, guaranteeing order for that key. If no key is set, messages are round-robin'd across partitions.

Real world: Use user_id as partition key so all events for user #42 are ordered. Use order_id for e-commerce so order lifecycle events (created → paid → shipped) stay in sequence.
📥

Offset

A unique, sequential ID assigned to each message within a partition. Consumers track their offset to know where they left off. Offsets are committed back to Kafka (or externally) so consumers can resume after a crash.

Real world: Consumer reads offset 1000, processes it, commits offset 1001. If it crashes, it restarts at 1001 — no data lost, no duplicate processing (with exactly-once config).
👥

Consumer Group

A set of consumers that divide the work of reading from a topic. Each partition is assigned to exactly one consumer in the group. If you have 6 partitions and 3 consumers in a group, each consumer reads 2 partitions. This is Kafka's horizontal scaling model.

Real world: Notification service has consumer group "push-workers" with 10 instances. Email service has group "email-workers" with 5 instances. Both independently consume the same order-events topic without interfering.
🔁

Replication Factor

Each partition is replicated across N brokers. One replica is the leader (handles reads/writes), the rest are followers (passive copies). If the leader broker dies, a follower is promoted. Standard production setup: replication factor = 3.

Real world: With RF=3, a topic can survive 2 broker failures without data loss. Netflix runs RF=3 for all critical topics.
🔒

ZooKeeper / KRaft

ZooKeeper was Kafka's metadata manager — tracking which brokers are alive, which broker leads which partition, and consumer group membership. KRaft (Kafka Raft) replaces ZooKeeper starting Kafka 3.3+, moving metadata management into Kafka itself. Fewer moving parts, simpler ops.

Real world: ZooKeeper was the #1 operational headache in Kafka deployments. KRaft eliminates an entire distributed system from your stack.
💬

Producer Acknowledgments (acks)

Controls durability guarantees when a producer sends a message:

acks=0 — Fire and forget. Fastest, but messages can be lost.
acks=1 — Leader writes to disk before acknowledging. Leader failure = possible loss.
acks=all — All in-sync replicas must acknowledge. Safest. Required for exactly-once.

Real world: Analytics events: acks=1. Payment events: acks=all. Choose based on what you can afford to lose.
💯

ISR (In-Sync Replicas)

The set of replicas that are caught up to the leader. Only ISR members can be elected as new leaders. A follower falls out of ISR if it lags behind by more than replica.lag.time.max.ms (default 30s). min.insync.replicas sets the minimum ISR size required for acks=all writes to succeed.

Real world: RF=3 + min.insync.replicas=2 + acks=all = gold standard production config. Survives 1 broker failure without data loss or write blocking.
🔄

Exactly-Once Semantics (EOS)

Kafka supports three delivery guarantees:
At-most-once: Messages may be lost, never duplicated. (acks=0, auto-commit offsets)
At-least-once: Messages never lost, but may be duplicated. (Most common default)
Exactly-once: No loss, no duplicates. Requires idempotent producers + transactional APIs.

Real world: Stripe uses exactly-once for payment processing. Most analytics pipelines use at-least-once with downstream deduplication — cheaper and simpler.
📈

Consumer Lag

The difference between the latest offset in a partition and the consumer's committed offset. Lag = how far behind a consumer is. Monitoring lag is the #1 operational metric for Kafka.

Real world: If your notification consumer has lag of 500,000, users are getting notifications 10 minutes late. Alert threshold: set based on SLA. Tools: Burrow, Kafka Exporter + Grafana.
📋

Schema Registry

A service (often Confluent Schema Registry) that stores and enforces schemas (Avro, Protobuf, JSON Schema) for Kafka messages. Producers register schemas. Consumers validate against them. Prevents breaking changes from silently corrupting downstream services.

Real world: Team A changes the order-events schema by removing a field. Without schema registry: Team B's consumer silently breaks at 3 AM. With schema registry: deployment is blocked with a compatibility error.
🔧

Kafka Connect

A framework for streaming data between Kafka and external systems (databases, S3, Elasticsearch, etc.) without writing custom code. Source connectors pull data into Kafka. Sink connectors push data from Kafka out.

Real world: CDC (Change Data Capture) with Debezium: stream every row change from PostgreSQL into Kafka automatically. Sink to Elasticsearch for full-text search. Zero application code.
🌊

Kafka Streams / ksqlDB

Kafka Streams is a Java library for real-time stream processing directly within your app — no separate cluster (unlike Flink/Spark). ksqlDB lets you write stream processing as SQL queries. Both handle windowing, joins, aggregations.

Real world: "Count orders per restaurant in the last 5 minutes" — a tumbling window aggregation. Zomato uses this for real-time dashboards showing live order volume per city.
🗝

Log Compaction

Instead of deleting old messages by time, Kafka can keep only the latest value per key. This turns a topic into a key-value changelog — perfect for maintaining materialized views or caches.

Real world: User profile topic with key = user_id. After compaction, the topic contains one record per user — always the latest profile. New consumers get the full current state on startup.
🏗

Key insight: Each consumer group gets its own independent view of the topic. Group A processing notifications doesn't affect Group B running analytics. Both track their own offsets. This is what "multiple consumers independently react to the same event" means in practice.

Partition parallelism rule: You can have at most as many consumers in a group as there are partitions. 3 partitions, 5 consumers = 2 consumers sit idle. 12 partitions, 3 consumers = each reads 4 partitions. Plan your partition count based on peak consumer parallelism.

When Kafka Shines

The five scenarios where Kafka is the right answer.
🔌

Decoupling Services

Multiple consumers independently react to the same event via consumer groups. Producer doesn't know or care who's consuming.

Example: Zomato order placed → Kafka → Push notification worker + Email worker + Analytics pipeline + Restaurant dashboard. Order service owns zero of this.
🔄

Event Replay & Auditability

Topics retain messages based on retention policy. Reprocess events, rebuild state, or debug production issues by replaying from any offset.

Example: Razorpay discovers a billing bug. Replays 7 days of payment-events through a fixed consumer to recalculate all invoices. No data loss.
🚀

High-Throughput Ingestion

Horizontally scales to millions of messages/sec across a cluster. Handles traffic spikes by absorbing bursts into partitions.

Example: Instagram ingests 1M+ likes/sec during peak hours. Kafka absorbs the burst. Downstream counters update async without blocking the like API.
📋

Ordering Guarantees

Messages within a partition are strictly ordered. Use partition keys to ensure per-entity ordering (all events for user #42 processed in sequence).

⚙

Event-Driven Pipelines

Analytics, notifications, recommendations, and search indexing consume asynchronously without blocking producers. True async microservices.

✘

When Kafka Is Overkill

Three scenarios where simpler tools win.
💤

One Producer, One Consumer, No Replay

If you have a single service producing messages and a single service consuming them with no need for replay, retention, or multiple consumers — SQS or Redis Streams is simpler and cheaper.

  • Why not Kafka: You're paying for broker management, partition planning, ZooKeeper/KRaft overhead for a use case a managed queue handles out of the box.
  • Use instead: AWS SQS, Redis Streams, or Google Cloud Pub/Sub
!
🔄

Request-Response Workflows

Kafka adds latency (batching, consumer polling intervals) and doesn't natively support request-reply patterns. If service A needs to call service B and wait for a response, use HTTP/gRPC.

  • Why not Kafka: Minimum consumer poll latency is ~10-100ms. Batching adds more. A synchronous gRPC call takes 1-5ms.
  • Use instead: gRPC, REST, or GraphQL
💸

Low-Scale CRUD Apps

If your app has minimal integrations and handles hundreds of requests/sec — the operational overhead of brokers, ZooKeeper/KRaft, partitions, consumer group management, and monitoring isn't worth it. A PostgreSQL-backed job queue (SKIP LOCKED) or a simple Redis list handles this with zero additional infrastructure.

Rule of thumb: If your team can't dedicate someone to Kafka ops, you probably don't need Kafka. Managed alternatives (AWS MSK, Confluent Cloud) reduce this but add cost.
The staff-level signal: In an interview, saying "I'd use SQS here instead of Kafka because we have a single consumer, no replay needs, and I want to avoid operational overhead" is 10x more impressive than defaulting to Kafka everywhere. It shows you understand tradeoffs, not just tools.
⚖

Pick RabbitMQ When

You need complex routing (fanout, headers, dead-letter), task queues with acknowledgments, or request-reply patterns. RabbitMQ's exchange model is more flexible for routing than Kafka's topics.

Example: Email service with priority queues — high-priority password resets route to fast workers, low-priority marketing emails go to slow workers.
☁

Pick SQS When

You want zero operational overhead, one producer/one consumer, and don't need replay. SQS is the "just works" option for simple async processing on AWS.

Example: Thumbnail generation — user uploads image → SQS message → Lambda resizes it. No brokers to manage. Scales automatically.

The System Design Interview

"Design a notification system for Zomato." Here's the mid-level vs staff-level answer.
"How would you design a notification system that sends push, email, and SMS when an order is placed?"
✘ THE REJECTED ANSWER
"The order service calls the notification service synchronously after placing the order. The notification service sends push, email, and SMS in sequence. If any of them fail, we retry inline."
Interviewer: "So if the SMS vendor is down for 30 seconds, your user stares at a loading spinner for 30 seconds after placing an order?"
Same question. Better answer.
✔ THE STAFF-LEVEL ANSWER
"The order service publishes an order.placed event to Kafka and returns 200 to the user immediately. Three independent consumer groups consume the event: push-notification-workers, email-workers, and sms-workers. Each scales independently. If SMS is down, push and email still work. The SMS consumer retries with exponential backoff from its last committed offset. I'd use user_id as the partition key to ensure per-user notification ordering — so a user doesn't get 'delivered' before 'order confirmed.' I'd pick Kafka over SQS here because we need multiple consumer groups on the same event and may want replay for debugging missed notifications."

The golden phrase: "I chose Kafka here specifically because [reason]. If this were a simpler use case with a single consumer and no replay, I'd use SQS instead." That one sentence tells the interviewer you think in tradeoffs, not tools.

"What if we need exactly-once delivery for payment notifications?"
✔ BONUS ANSWER
"I'd use idempotent producers (enable.idempotence=true) with acks=all on the producer side, and transactional consumers that commit offsets and database writes atomically. But honestly, for most notification use cases, at-least-once with idempotency at the consumer is simpler — store a notification_id in a dedup table and skip if already sent. Exactly-once end-to-end across Kafka and external systems (email vendor) is architecturally impossible — the external system doesn't participate in Kafka transactions. So consumer-side dedup is the practical answer."
🎯

Key Takeaways

What to remember when Kafka comes up in interviews or architecture reviews.
⚖

Justify the Tool

"Why Kafka over SQS?" is the question. Multiple consumers, replay, ordering, and high throughput are the valid answers.

🔑

Partition Keys Matter

Your partition key determines ordering and parallelism. Wrong key = hot partitions. No key = no ordering. Think about it early.

📈

Monitor Consumer Lag

Lag is the single most important Kafka metric. If consumers can't keep up, nothing else matters.

💤

Simpler Is Often Better

SQS for single-consumer async. RabbitMQ for complex routing. Kafka for event streaming at scale. Use the smallest tool that fits.
